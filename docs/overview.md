# プロジェクト概要

## 背景と課題

リーナーテクノロジーズは toB SaaS を自社開発・運用しており、プロダクトごとに週次でインフラモニタリング会（モニ会）を実施している。

課題は**各プロダクトチームにインフラのスペシャリストがいないこと**。そのため会の進行、ペインポイントの発見、改善点の抽出が属人的で難しかった。そこで AI エージェントにインフラメトリクスを読み込ませ、**分析からネクストアクション候補の提示までを支援**させるのがこのプロジェクトの狙い。

## 対象プロダクト

| 略称 | 正式名 | Datadog `team` タグ |
| --- | --- | --- |
| LP | リーナー見積 | `lp` |
| PU | リーナー購買 | `pu` |
| FJ | リーナーコネクト | **`connect`**（`fj` ではない） |

## 設計思想

### monitor 駆動

閾値判定とスパイク検知を**エージェント側でやらない**。Datadog monitor（Terraform で管理、`leaner-terraform` の `environments/datadog/`）に委譲する。

#### なぜこの方式にしたか

エージェント自身に閾値を判断させていた時期に、次の3つの問題が起きていた。

1. **緊急度の認識が人間とエージェントで一致しなかった。** エージェントが「要対応」と書いたものが人間の感覚では静観でよく、逆に人間が気にする事象がレポートで軽く扱われる。レポートを読んで議論する場（モニ会）で、まず認識合わせから始めることになり本題に入れない。
2. **AI モデルによって閾値がバラバラだった。** 同じメトリクスを渡してもモデルが変われば判定が変わるため、週をまたいだ比較が成立せず、レポートとして積み上がらなかった。
3. **メトリクス読み込みでトークンを大量消費していた。** 閾値を自前で判断するには広く生メトリクスを引く必要があり、コストが膨らんでいた。

そこで **Datadog monitor に warning / critical を定義し、閾値の認識をそこで一致させる**ことにした。

#### 得られた効果

- **緊急度合いの認識が人間とエージェントの間で一致した。** monitor の warning / critical が両者にとって同じ意味を持つため、レポートに載る発火の事実がそのまま議論の出発点になる。
- **monitor の alert が起点になり、深掘りの対象が定まった。** 「鳴った monitor の発火ウインドウを掘る」という形で、エージェントに原因調査をさせられるようになった（トリガ制の由来）。
- **トークン消費の最適化にも寄与していると見込んでいる。** 閾値判定のために広く生メトリクスを引く必要がなくなり、深掘りも発火ウインドウに絞られるため。ただし削減幅を実測したわけではない。

#### 運用上の帰結

- 閾値がサーバ側の決定論的な monitor に一元化され、レポートに載る severity と実際のアラートが必ず一致する（色は severity ではなく「読者への要求」を表す → [monitors.md](monitors.md#評価ステータスのルール)）。
- エージェントの仕事が「シグナルの収集と解釈」に絞られ、毎回同じ判定結果が再現する。
- 閾値の変更が Terraform の1箇所で済む（レポート側の記述と二重管理にならない）。
- **monitor がない領域はレポートで扱わない。** シグナルソースがないものを扱うと、閾値をエージェントが持つ元の状態に戻ってしまう。扱いたければ monitor を追加してから取り込む（現状の穴は [improvement-backlog.md](improvement-backlog.md) の G）。

したがって **monitor の閾値がレポートの判定基準そのもの**。閾値を変えたいときは Terraform の monitor を変える。**エージェントが独自に閾値を持ち出して判定してはいけない** — この方式が解決した3つの問題がそのまま再発する。

#### 責務分離（設計中）

「どこまでが monitor の仕事で、どこからがレポートの仕事か」は当初明文化されておらず、境界が腐り始めている（[improvement-backlog.md](improvement-backlog.md) の L がその症状）。分離の設計案を [issues/001-monitor-report-responsibility.md](issues/001-monitor-report-responsibility.md) にまとめた。判断基準は次の一文:

> その判断は、読むモデル・読む人間が変わっても同じ結果になるべきか。Yes なら monitor の責務、No（文脈解釈が本質）ならレポートの責務。

### OODA ループ

エージェントは **Observe（事実）と Orient（解釈・先週比・異常の切り分け）を厚く書き、Decide / Act は候補提示のみ**にする。決めるのは会に参加する人間。

- **Observe**: monitor 状態、アラート発火イベント、SLO 数値、先週比トレンド。
- **Orient**: 悪化の「主体」と「上流原因」を分けて書く。瞬間スパイクか持続的な劣化かを切り分ける。
- **Decide / Act**: 🔴 緊急（今週中に決める）/ ⛔ 滞留（3週以上）/ 🟡 要検討（次週も再発したら）/ 🟢 継続観察 / ℹ️ 低優先・恒久課題 で候補を並べる。

### critical 駆動の深掘り

アプリのトレース詳細調査は**インフラ側の異常シグナルが出た週だけ**行う（トリガ制）。シグナルのない週に per-endpoint 探索をすると、import 系（レスポンスがデータ量に比例する）の誤検知とトークン消費しか生まない。恒常的な劣化は SLO と Sentry がカバーする。

## 運用サイクル

| チーム | 対象ウインドウ | 生成タイミング |
| --- | --- | --- |
| LP | 水曜 00:00 〜 火曜 23:59 JST | 水曜 09:00 JST（cron `0 9 * * 3`, jitter 最大 460秒） |
| PU / FJ | 金曜 00:00 〜 木曜 23:59 JST | 金曜 09:05 JST（cron `5 9 * * 5`, jitter 最大 50秒） |

いずれも**ウインドウがクローズした直後**に生成する。週クローズ前だと累積系メトリクス（リクエスト数・ジョブ件数・ALB カウント）を過少計上する。

## 自動実行の仕組み

Claude Code のスケジュールタスクとして登録されている（`mcp__scheduled-tasks__list_scheduled_tasks` で確認できる）。

| taskId | SKILL.md | 対象 |
| --- | --- | --- |
| `infra-report-for-lp` | `~/.claude/scheduled-tasks/infra-report-for-lp/SKILL.md` | LP のみ |
| `create-weekly-report-for-infra-monitoring` | `~/.claude/scheduled-tasks/create-weekly-report-for-infra-monitoring/SKILL.md` | PU と FJ（サブエージェントで並列） |

各 SKILL.md は**薄いエントリポイント**で、実質的な指示は本リポジトリの agent 非依存 skill（`skills/weekly-infra-report/`）とプロダクト固有値（`templates/<lp|pu|fj>.md`）にある。スケジュールタスク側の SKILL.md が持っているのは「対象ウインドウ」「重複防止」「参照先の所在」「monitor 取得クエリ」だけ。

⚠️ **2026-09-15 時点でスケジュールタスクの SKILL.md はまだ Notion のプロンプト＆テンプレートページを参照している。** 参照先の差し替えが未了（[improvement-backlog.md](improvement-backlog.md) の M）。

Notion 上のレポートページの作成者は Notion インテグレーションユーザ（`notion_user-1aad872b-…`）として記録される。

## リポジトリの位置づけ

このリポジトリは基本的にドキュメントの置き場である。**エージェントへの実行指示（skill ＋ `templates/`）と、運用知識・落とし穴（`docs/`）**を持つ。唯一のコードは `scripts/validate-report.py`（依存なしの検証スクリプト）で、Notion へ書き込む前に完成成果物の構造を機械的に検査する。

実行指示は 2026-09-15 に Notion のプロンプト＆テンプレートページから移設し、同日**3層に分割**した（手順 = skill / レポート構成 = `templates/report.md` / 固有値 = `templates/<product>.md`）。**以降はこちらが正**で、Notion 側のページは stale。分割の狙いは、3プロダクトで約7割あった重複の解消と、トリガ OFF の週に調査手順を読み込まないことによるトークン削減（実測は [improvement-backlog.md](improvement-backlog.md) の N）。

- 生成手順（3プロダクト共通）→ **このリポジトリの `skills/weekly-infra-report/`**
- レポート構成 → **このリポジトリの `templates/report.md`**
- プロダクト固有値 → **このリポジトリの `templates/<lp|pu|fj>.md`**
- 閾値と monitor 定義 → `leaner-terraform` の `environments/datadog/`
- 実行スケジュールとエントリプロンプト → `~/.claude/scheduled-tasks/`
- 運用知識・改善課題 → **このリポジトリの `docs/`**
- 出力前の構造検査 → **このリポジトリの `scripts/validate-report.py`**
- 生成したレポートの置き場 → Notion のプロダクト別 DB（**出力先であって指示の置き場ではない**）
