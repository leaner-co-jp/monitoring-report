# monitor インベントリと閾値

monitor は `leaner-terraform` の `environments/datadog/` でデプロイされている。**monitor の実値がレポートの判定基準そのもの**（二重管理しない）。

閾値をここに集約している理由は、**人間とエージェントの間で緊急度の認識を一致させる**ため。エージェントに閾値を判断させると、モデルごとに判定がぶれて週をまたいだ比較が成立しなくなる。経緯は [overview.md](overview.md#なぜこの方式にしたか)。

取得は必ず1コール:

```
search_datadog_monitors  query="tag:report:weekly team:<lp|pu|connect>"  include_tags=["*"]
```

⚠️ 応答はページングされる。`is_truncated` が立っていたら `start_at` を進めて全件取る。

## 評価ステータスのルール

**色（🔴🟡🟢⛔）は「読者に何を要求するか」にのみ使う。monitor の発火状況には色を付けない。** 発火は判定ではなく事実なので、**件数と継続時間**で書く（例: `critical 2件 / warning 1件（最長11分、いずれも自動復旧）`）。

- 🔴 **今週中に人の判断が必要** — モニ会でその場で決める
- 🟡 **次週も再発したら判断** — 覚えておいて次週の同項目を見る
- 🟢 **記録のみ / 対応不要** — 読み飛ばして良い
- ⛔ **3週以上滞留した項目**（🔴 より強い要求） — オーナーを決めるか、正式に「やらない」と決める

絵文字には必ず**根拠の数値を併記**する（絵文字単体での使用は不可）。

### 対応要否の当て方

エージェントに裁量を残すと週ごとに判定がぶれる。順序つきの規則で決め、**判定材料は monitor の発火とその波及だけ**にする（新しい閾値を持ち出してはいけない）。

**§1「今週の判定」** — 上から当てて最初に一致したものを採る:

1. レポート生成時点で**発火中**の monitor がある → 🔴
2. SLO の**エラーバジェット枯渇・バーンレート** monitor が週中に発火した → 自動復旧でも 🔴
3. 週中に発火して自動復旧した monitor があり、**波及**（SLO / 他レイヤ / 観測されたユーザー影響）が確認できる → 🔴
4. いずれも該当しない → 🟢（記録のみ。**発火があってもここに落ちる**）

§2 にインシデント節がある週は、§1 の判定を各節の対応要否のうち**最も重いもの**とする（max ルール。独自判断で緩めない）。

判定が 🟢 でも Decide / Act に ⛔ / 🔴 が残っている週は、**判定ブロック内にその件数を1行で示す**（🟢 が読み残しの口実にならないようにする）。

**Decide / Act の各項目** — 読者がその項目に対して何をすべきかで付ける。🔴 今週中に決める / ⛔ 3週以上滞留（オーナーを決めるか、正式に「やらない」と決める）/ 🟡 次週も再発したら決める / 🟢 記録・観察のみ。3週以上滞留した項目を 🟡 のまま持ち越さず ⛔ に上げるのは、「要検討」に置き続けても動かないことが実証されたため。

### 判定と発火件数が食い違って見える週

規則4では「critical が出ているのに 🟢」になる。このとき**同じブロック内に「なぜその判定なのか」を必ず1行添える**（読み手が矛盾と受け取るのを防ぐため）。

severity（warning / critical）は monitor だけが発行するもので、レポートは**書き換えない**。色を severity から切り離したのはこのためで、`critical 2件` は必ずその語のまま残る（[issues/001](issues/001-monitor-report-responsibility.md) 原則1）。台帳の `monitor発火` 列も状態語（OK / Warn / Alert）ではなく `発火なし` / `critical 1回 / 10分` のように事実で書く。先週比トレンドは方向と数値を添えるために使う。

## 閾値（3プロダクト共通）

| 指標 | 🟡 warning | 🔴 critical |
| --- | --- | --- |
| ECS メモリ %（全サービス共通） | 80% | 95% |
| ECS CPU %（vCPU 正規化、全サービス共通） | 90% | 95% |
| RDS Writer コネクション数 | 9000 | 9500（LP の現上限 10000） |
| RDS Writer CPU % | 75% | 90% |
| ALB 5xx（elb）エラー率 | 0.5% | 1.5% |
| ALB Healthy ホスト数 | — | < 1（全断） |
| Job p95 レイテンシ | — | anomaly（agile, 2σ 乖離） |
| SLO エラーバジェット | — | 枯渇（consumed > 100%） |
| SLO バーンレート（1h / 5m） | — | > 14.4 |

⚠️ **ECS CPU % は vCPU 正規化値で評価する** — `cpu.percent / (cpu.task.limit / 1e9)`。生の `cpu.percent` は単一 vCPU 基準なので複数 vCPU 割当のタスクで 100% 超が出る。閾値（90 / 95）と直接比較してはいけない。詳細は [datadog-mcp-tips.md](datadog-mcp-tips.md)。

⚠️ **Worker 系 ECS CPU monitor（`max(last_10m) > 95`）には校正不良の既知課題がある**（2026-07-29 指摘、3プロダクト共通）。0.5 vCPU クラスのワーカーは CPU% が二値的（平常時 ~10% ⇔ ジョブ実行時 ~98%）に振れるため、瞬間値の max 判定では**仕様どおりの稼働が critical として発火する**。「健全に忙しい」と「不健全」をレベル閾値で分けることは原理的にできず、分けられるのは継続時間だけ。非事象の critical が severity の信頼を毀損している。詳細な害の分析と改善案（`min(last_15m) > 90` への変更等）は [improvement-backlog.md](improvement-backlog.md) の L。

## monitor がない = レポートで扱わないもの

monitor 駆動方式では**シグナルソースがないものは扱わない**。扱いたければ monitor を追加してから取り込む。

- WAF（PU のダッシュボードにはあるが monitor なし。LP・FJ はダッシュボードにもなし）
- SES（PU・FJ のダッシュボードにはあるが monitor なし）
- RDS Reader（専用 monitor がないため判定対象外。参考値として記載）
- アプリ起因の 5xx（Sentry 管轄）
