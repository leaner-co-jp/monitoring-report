# 評価ステータスルール

**色（🔴🟡🟢⛔）は「読者に何を要求するか」にのみ使う。monitor の発火状況には色を付けない。** 発火は判定ではなく事実なので、**件数と継続時間**で書く（例: `critical 2件 / warning 1件（最長11分、いずれも自動復旧）`）。

- 🔴 **今週中に人の判断が必要** — モニ会でその場で決める
- 🟡 **次週も再発したら判断** — 覚えておいて次週の同項目を見る
- 🟢 **記録のみ / 対応不要** — 読み飛ばして良い
- ⛔ **3週以上滞留した項目**（🔴 より強い要求） — オーナーを決めるか、正式に「やらない」と決める

絵文字には必ず **根拠の数値を併記**する（単体使用は不可）。

## §1「総合ステータス」の判定色の当て方

上から当てて最初に一致したものを採る。週ごとに判定がぶれないための順序規則で、**新しい閾値を持ち出してはいけない**（材料は monitor の発火とその波及だけ）:

1. レポート生成時点で**発火中**の monitor がある → 🔴
2. SLO の**エラーバジェット枯渇・バーンレート** monitor が週中に発火した → 自動復旧でも 🔴
3. 週中に発火して自動復旧した monitor があり、**波及**（SLO / 他レイヤ / 観測されたユーザー影響）が確認できる → 🔴
4. いずれも該当しない → 🟢（記録のみ。**発火があってもここに落ちる**）

規則4で「critical が出ているのに 🟢」になる週は、**同じブロック内に「なぜその判定なのか」を必ず1行添える**（読み手が矛盾・格下げと受け取るのを防ぐため）。判定が 🟢 でも Decide / Act に ⛔ / 🔴 が残る週は、判定ブロック内にその件数を1行で示す。

**severity（warning / critical）は monitor だけが発行する。レポートは書き換えない。** 色を severity から切り離したのはこのためで、`critical 2件` は必ずその語のまま残る。

## 共通の注意

- **色は monitor 状態が一次ソース**。手順1の `status` と手順2の今週の発火イベントで決める。
- 手順5 の先週比トレンドは、各指標に**方向（上昇／下降）と数値**を添えるために使う（色そのものは monitor に従う）。ただし warning 閾値への接近が複数週続く場合は 🟡 として補記してよい。
- Rails レイテンシなど **monitor の直接閾値が無い指標**は、SLO（APIレスポンスタイム）の状態と先週比トレンドで評価する。**レイテンシ単体では色を付けない。**
- **ECS CPU % は vCPU 正規化値**（`cpu.percent / (cpu.task.limit / 1e9)`）で評価する。生の `cpu.percent` は単一 vCPU 基準で 100% 超が出るため、閾値（90 / 95）と直接比較しない（monitor のクエリと同じ式）。**素の scalar:max は瞬間ピークのアーティファクトなので閾値評価に使わない。**
- **monitor が存在しないリソースは判定対象外の参考値**として扱う。色を付けず、独自閾値で評価しない。数値は §3.1 の台帳にのみ記録し、先週比 ±20% 以上動いた週は §1 の「monitor 以外で動いた指標」に書く。
- **上表に無い閾値を持ち出して判定しない。** 過去のテンプレートには monitor の裏付けがない独自閾値（SLO の `EBR < 20%`、Worker-Long の「週4回以上のスパイク / 70% 超え」）が書かれていたが、これらは撤去した。同種の判断が必要になったら monitor を作る。
