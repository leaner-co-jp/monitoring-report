## 使う Datadog MCP ツール

| ツール | 用途 |
| --- | --- |
| `search_datadog_monitors` | monitor の状態を一括取得 |
| `aggregate_events` | アラートの件数・概況を軽量に集計（本文が不要なとき） |
| `search_datadog_events` | アラートの発火・復旧イベントを時系列で取得 |
| `get_datadog_metric` | メトリクスクエリ。先週比トレンドの補足取得に使う。`response_format` は `timeseries`（既定）と `scalar` |
| `get_datadog_dashboard` | ダッシュボード構成・ウィジェット値の取得 |
| `get_datadog_metric_context` | メトリクスのタグ／メタデータ探索（補助、必要時のみ） |
| `search_datadog_spans` | 個々のスパンを duration 降順などで直接列挙。単発の長時間トレース／重い SQL の検知に使う（手順4-c）。集約では消える外れ値を拾うのに必須 |
| `get_datadog_trace` | trace_id からトレース全体の waterfall を取得し支配スパンを特定 |
| `aggregate_spans` | スパンの集計（p95 / max など）。`group_by` 付きは 0 buckets を返すことがあるため、最悪スパンの特定は `search_datadog_spans` の duration 降順を主軸にする |

<aside>
📌

- 各ツール呼び出しでは `telemetry.intent`（英語・短く・値や PII は含めない）を必須指定する。
- 期間は各ツールの `from` / `to` に直接渡す。ISO 8601（`2026-05-27T00:00:00+09:00`）・Unix 秒・相対表記（`now-1d`）のいずれも可。**今週 = {{P.window_ja}}の7日間、先週 = その前の7日間を別々に取得して比較**する。
- `scalar` は「期間内を1値に集約」する出力。集約方法は各クエリオブジェクトの `aggregator`（`avg`/`sum`/`min`/`max`/`last`）で決まる（クエリ接頭辞 `p50:` 等とは別物）。**avg と max を両方見たい指標は `aggregator` を変えて2回呼ぶ**（または `timeseries` で取得して算出する）。
- レイテンシ系メトリクス（`trace.*`）は秒単位。ms 表記にするには ×1000。

</aside>

## 取得の原則（生成を途中で止めないため）

取得結果が大きすぎて応答上限を超え、ツールが一時ファイルへ退避した結果、レポート生成が途中で止まった事例がある。再発防止のため次の3点を守る:

1. **大きい取得結果をそのまま扱わない。** まず件数・概況を集計し、必要な範囲だけ詳細を取る（手順2・手順3・§0.5）。全件・全文・フル構成の取得を既定にしない。
2. **一時ファイルのパスを後続処理の前提にしない。** 大きな応答が一時ファイルへ退避されたら、そのレスポンスで返った `file_path` を**直ちにその場で読む**。後続の手順で同じ内容が必要になったら、パスを再利用せず**元の Datadog / Notion API を小さい条件で再問い合わせする**（一時ファイル名は呼び出しごとに変わるため、再利用は失敗しやすい）。
3. **要点は会話内の構造化メモとして持つ。** monitor ID / 発火時刻（JST + epoch ms）/ 週次の集計値 / 前週の Decide / Act 候補は、取得した時点で短い箇条書きに写し取り、以降はそのメモを参照する。

## 取得順（この順に固定する）と失敗時の代替

段階が失敗してもレポート全体を止めない。該当行だけ `⚠️ 取得不可: <理由>` と書いて次へ進む。**例外は `templates/report.md` と `templates/<product>.md` が読めない場合だけで、そのときは生成を停止する。**

1. **テンプレートの取得**（`templates/report.md` ＋ `templates/<product>.md`） → 失敗なら**即停止**し `⚠️ 取得不可` を報告（構成を推測で補わない）
2. **monitor 一覧と現在状態**（手順1） → 失敗なら monitor 状態を取得不可とし、手順2の発火件数で Observe を代替
3. **今週・先週のアラート件数の集計**（手順2 前段） → 失敗なら手順1の現在状態のみで書き、週中の一過性発火は取りこぼしとして明記
4. **今週発火があった monitor と時間帯に限った詳細イベント取得**（手順2 後段） → 失敗なら「発火ウインドウ取得不可」と明記し、手順4 は日付単位の粗いウインドウで進める
5. **週次メトリクス**（手順5）を**小さいクエリ群に分割**して取得 → 失敗した指標だけ台帳を取得不可にする（1本の失敗で全体を止めない）
6. **SLO 数値**（手順3） → 失敗なら SLO monitor の状態を事実として採用し、SLI / エラーバジェット残は取得不可と明記
7. **前週レポート**（§0.5）を一覧から1件だけ特定し、**必要な章だけ**読む → 失敗なら「前週レポート参照不可」と明記
8. **検証チェック**（`references/output.md`）を通してから Notion に書き込む

## 手順1. monitor 状態の一括取得（Observe の主軸）

`search_datadog_monitors` に `query="tag:report:weekly team:{{P.team}}"`、`include_tags=["*"]` を指定し、{{P.name}}の週次レポート対象 monitor をまとめて取得する（1コール）。

- monitor の `status` は**色に写さない**。`Alert` / `Warn` = 「現在発火中」、`OK` = 「現在発火なし」として**事実で記録**する（色の付け方は `references/evaluate.md`）。`No Data` は `⚠️ 取得不可` と明記する。これは取得時点の現在状態だけを示し、`OK` でも対象ウインドウ中に発火がなかった根拠にはならない。

<aside>
⚠️

monitor は直近10分など短いウインドウで評価するため、現在の `status` だけでは週中に発生して復旧済みの一過性シグナルを取りこぼす。週次の傾向は手順2・5 で補う。

応答はページングされる。`is_truncated` が立っていたら `start_at` を進めて全件取る。**取り漏らすと「発火していない」と誤報告する。**

</aside>

## 手順2. アラートシグナルの収集（今週／先週）

**週全体のイベントを全件取得してはいけない。**`source:alert team:{{P.team}}` には復旧・更新・通知のイベントも大量に含まれ、想定以上に膨らんで応答上限を超える。次の2段階に分ける:

### 2-a. まず総件数を集計する（本文は取らない）

1. `aggregate_events` に `query="source:alert team:{{P.team}}"`、`from` / `to` に今週・先週をそれぞれ指定し、**`group_by` なしの COUNT を必ず先に取得**する。両方の取得が終わるまで grouped 集計を実行しない。この総件数には Warn / Triggered / Recovered などが含まれ、発火回数そのものではない。
2. monitor ごとの grouped 集計は候補を絞るための**任意の最適化**とする。使う場合は、今週・先週ごとに bucket の件数合計を 1 の ungrouped 総件数と照合する。`@monitor_name` を含む grouping field は欠損・名称変更・facet の不安定さがあるため、空 bucket、合計不一致、不明 bucket があれば信頼しない。**grouped 集計が 0 buckets でも、イベント0件の根拠にはならない。**
3. 該当週の ungrouped 総件数が1件以上なのに grouping が空または不完全なら、手順1で取得した `report:weekly` monitor の ID / 名前を全件列挙し、各 monitor について `search_datadog_events` で **Triggered を必ず検索**する。monitor ID で絞れる環境では ID を優先し、未対応なら完全な monitor 名にフォールバックする。日別集計などから候補日・時間帯を絞れる場合は狭め、絞れない場合も「1 monitor × 1対象ウインドウ」に限定する。**team 全体 × 週全体の本文取得には戻らない。**

### 2-b. 候補 monitor だけ詳細を取る

照合済みの grouping で候補になった monitor、または 2-a のフォールバックで見つかった monitor に限り、`search_datadog_events` を**その monitor と候補時間帯に絞って**引く。

- Warn / Triggered / Recovered は混ぜずにそれぞれ検索・記録する。今週の **Triggered がアプリ調査トリガを ON にするイベント**であり、Warn / Recovered だけでは ON にしない。
- 各状態遷移の UTC 時刻を JST（UTC+9）へ変換して一致を検算し、対象ウインドウとの境界も確認する。Warn → Triggered → Recovered の対応を時系列で確認し、発火から復旧までの継続時間を記録する（例: 火曜 03:00 Triggered → 03:18 Recovered、18分）。境界をまたぐ場合はその旨を明記する。
- **発火ウインドウの epoch ms は取得した時点で会話内のメモに写し取る**（手順4 の APM 調査で使う。一時ファイルからの読み直しに頼らない）。

今週・先週の Warn / Triggered の件数と深刻度を比較し、増減を「変化」として明示する。先週は比較に必要な範囲だけ取得し、本文を広く読まない。

<aside>
💡

件数の入口は `aggregate_events` の ungrouped COUNT が軽量。grouping は照合できた場合だけ絞り込みに使い、発火ウインドウの正確な epoch は monitor と時間帯を限定した `search_datadog_events` で取る。

</aside>

シグナルの深刻度ごとの扱い:

- **warning**: 閾値接近の予兆。変化として記録し、複数週続く場合は傾向として Orient に書く。
- **critical**: 早急な対応が必要になり得る。**手順4 のアプリ調査トリガを ON にし、発火ウインドウに絞って原因を掘り下げる**。

## 手順3. SLO 数値（SLI / エラーバジェット残）

monitor は SLO の「状態」（枯渇／急消費の有無）を返すが、SLI % とエラーバジェット残 % の**数値**は返さない。数値は以下で補完する:

- **ダッシュボードのフル取得で SLO 値を探してはいけない。** `get_datadog_dashboard` のフル取得は重く、応答上限超過と一時ファイル退避の主要因になったうえ、SLI / EBR / Bad events の抽出も安定しなかった。SLO 数値専用の取得経路を上から順に試し、取れた時点で止める:
    1. **SLO 専用のツール／API が使えるならそれを使う。**（`list_datadog_skills` / `load_datadog_skill` に SLO 向けの取得手順が用意されていないか先に確認する）
    2. 使えない場合は、ダッシュボードの全構成ではなく **SLO 対象のデータだけを引く経路**を使う（{{P.name}}の2 SLO ID に限定した `get_datadog_metric` の SLO 系メトリクスなど）。取得は SLO ごとに小さいクエリへ分ける。
    3. それも取れない場合は、**手順1 の SLO monitor の状態を事実として採用**し、SLI % / エラーバジェット残 % は毎回明示的に `⚠️ 取得不可: <理由>` とする（推測値や前週値で埋めない）。
- 対象 SLO ID は「対象（プロダクト固定値）」の表を参照。
- 取得できない値は `⚠️ 取得不可: <理由>` と明記する（省略不可）。

## 手順4-a. アプリ調査トリガの判定（必須・毎週）

以下のいずれかが**今週（集計期間内）**に該当すれば「アプリ調査トリガ ON」とする:

- 手順2で今週の Triggered を確認（手順1の現在状態だけでは対象ウインドウ中の発火有無を判定しない）
- 手順3で SLO が劣化（エラーバジェット消費の進行・バーンレート警報・SLI 低下）

トリガ判定の結果（ON / OFF と根拠の monitor / event / SLO、ウインドウの epoch ms）を**テンプレート §1 の「アプリ調査トリガ」**に必ず明記する。critical シグナルがあった場合はそれを最優先で調査する。

- **ON の週** → `references/investigate.md` を読んで手順4-b 以降に進む。
- **OFF の週** → `references/investigate.md` は**読まない**。テンプレート **§2（調査）を見出しごと出力しない**（「該当なし」の見出しすら出さない）。§1 の「アプリ調査トリガ」に OFF と明記し、「インフラ / SLO 異常なし」と書く。数値は手順5 で取得し **§3.1 の台帳に記録**する（詳細調査はしない）。Rails レイテンシの恒常ドリフトは SLO（APIレスポンス）と Sentry に委譲する旨を §3.3 に明記してよい。

## §0.5 前週レポートの参照

出力先 DB（`{{P.db_name}}`）を作成日時の降順で **1件だけ**取得して最新ページを特定する（`ORDER BY datetime("作成日時") DESC LIMIT 1`。タイトルプロパティは `{{P.title_prop}}`）。

**前週レポートの全文は取得しない。** 必要なのは §1 の「Decide / Act 候補」と §3 の「前回 Decide / Act の反映状況」だけなので、**その該当箇所に絞って読む**。全文取得は応答上限を超えて一時ファイル退避を招き、生成が止まる原因になる。読み取った候補は会話内に短い箇条書きとして写し取り、以降はそのメモを参照する（一時ファイルのパスは再利用せず、再度必要になれば Notion API を小さい条件で引き直す）。

レポートには次の2つを明記する:

- 先週比セクションへの引用
- **前回の Decide / Act 候補が今週どう反映されたか**

未検出なら「初回扱い」と明記し、ダッシュボード内の calendar_shift データだけを使う。
