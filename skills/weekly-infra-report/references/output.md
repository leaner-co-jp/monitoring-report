# 出力ルール・日本語表現・検証チェック

## 出力ルール

- **数値はすべて単位付き**（ms, %, req, MiB / GiB）。
- 比較は「今週: X / 先週: Y / 差分: ±Z（±W%）」。
- 推測・主観は `(推定)` を付けて事実と分離する。
- データ取得に失敗した場合は `⚠️ 取得不可: <理由>` と明示する（省略不可）。

### 出力構成（テンプレート §1〜§3）

構成の規則（2階層・5原則・空枠の扱い・色の決め方）は `templates/report.md` 冒頭の運用ガイドが唯一の定義。手順側が付け加えるのは1点だけ:

- monitor が鳴っていない（または monitor が存在しない）指標で先週比 ±20% 以上動いたものは §1 の「monitor 以外で動いた指標」に書く。monitor のカバレッジの穴に気付く唯一の入口なので**省略不可**。発火回数の増減を書くときは必ず分母（閾値超過サンプル数／総サンプル数）と最長継続時間を併記する（分母なしの「N倍」は書かない）。

### 入力 JSON の書き方

レポート本文は `bin/weekly-report render` が組み立てる。エージェントは `bin/weekly-report stub` で作った入力 JSON の値を埋めるだけ。各スロットに何を書くかは `templates/report.md` の「ガイド:」にある。

- **文字列のスロット**（`status.summary` など）: 空にしない。
- **配列のスロット**（`signals.critical` など）: 1要素が箇条書きの1行。該当がなければ `[]`（「該当なし」等は render が出す）。要素に改行を入れない。
- **`metrics`**: キーは表の「指標」列と一字一句同じ名前。§1 の表と §3.1 の台帳に同じ名前の行があれば、同じ値が両方に入る。雛形にあるキーだけを埋める（テンプレートの固定セル、例えば `—` や `参考値` は書き換えられない）。取得できなかった値は `⚠️ 取得不可: <理由>` と書く。
- **`incidents`**: §2 のインシデント1件が1要素（形は雛形の `_incident_example`）。発火がない週は `[]` にすると §2 が節ごと出力されない。節番号・「記録のみ / 次週判断 / 今週判断」の文言は render が付ける。
- **monitor への言及**: `[<monitor 名>](https://app.datadoghq.com/monitors/<ID>)（#<ID>）` の形だけを使う。

運用ガイド・「ガイド:」・テンプレートの説明文は render が自動で落とす。ドメイン文脈を伝える注記（§2 冒頭の「調査時の前提」、§3.1 の注記、FJ の elb 防御シグナルなど）は render が残す。

### 調査リンク規約（Decide / Act と各 finding に添える）

site は `app.datadoghq.com`、markdown の `[ラベル](URL)` 記法。具体形はテンプレート冒頭の「🔗 調査リンク」。

- **期間レンジを見せる用途はダッシュボード**: `/dashboard/{{P.dashboard}}?from_ts={{F}}&to_ts={{T}}`（epoch ms）。広いウインドウを確実に反映する。
- **特定インシデント時刻の点的な調査はトレース探索**: `/apm/traces?...&end={{incident_epoch_ms}}&paused=true`。⚠️ `/apm/traces` は `storage=hot` のため**広い `start` を無視し、end − 15分にクランプ**する → インシデント時刻に `end` を合わせ、15分ウインドウで使う（週レンジには使わない）。`&paused=true` でウインドウを固定する。
- **週全体で重い endpoint / resource を順位付けする**なら APM サービスページ: `/apm/services/{{P.api_service}}?env=production&start={{F}}&end={{T}}`（Rails）/ `.../{{P.worker_service}}`（Job）。
- **monitor は名前・リンク・ID の合わせ技で書く**: `[<monitor 名>](https://app.datadoghq.com/monitors/{{monitor_id}})（#{{monitor_id}}）`。本文で monitor に言及するときは `mon 12345` のような ID 単独の略記を使わず、必ずこの形でクリックでき・一意に特定でき・人間が読んで分かる3点を満たす。
- アラートイベント本文の埋め込みリンクと `get_datadog_metric` 応答の `metrics_explorer_url` は **Datadog 生成のため再利用が最も安全**。手組みより優先する。

## レポートの日本語表現

レポートは**自然な日本語**を心がける（英語・カタカナの直訳調を避け、読み手が日本語として無理なく読める表現にする）。例:

| 修正前（違和感あり） | 修正後 |
| --- | --- |
| sustained peak (1h) / 1h sustained peak | 1時間平均の持続ピーク／1時間平均でならした持続的なピーク |
| sustained は低位 | 持続的な使用率は低位 |
| sustained な劣化 | 持続的な劣化 |
| critical 閾値をクロス / critical をクロス | critical 閾値を超過／突破 |
| 瞬間バースト / 大量バースト | 瞬間的な集中／短時間に大量実行 |
| latency は…と軽く | 処理時間は…と軽く |

<aside>
📌

技術用語を無理に訳す必要はない。monitor 状態の英語（OK / Warn / Alert）や固有名詞（monitor 名・メトリクス名・`resource_name`）はそのまま使ってよい。地の文が英語直訳調にならないようにするのが狙い。

</aside>

## 検証（render が機械的に確かめること）

`bin/weekly-report render` は完成形を作ったあと、次を検証して1つでも外れたら**全件を列挙して失敗する**（Notion 用の本文を書き出さない）。エラーは入力 JSON を直して解消し、render をやり直す。

| 検証 | 外れる例 |
| --- | --- |
| タイトルが固定形式 `YYYY/MM/DD - MM/DD <固定部>` で、期間が{{P.window_ja}}の閉じた7日間 | `… 週次レポート 2026/10/07〜10/13` |
| 見出しの並びがテンプレートと一致（§2 は発火がある週だけ） | 独自の「§4 収集記録」を足す / 「評価ルール」を落とす |
| テンプレートの固定行がすべて同じ順序で残っている | 「色の意味」の表の文言を言い換える |
| 指標表の行がテンプレートと過不足なく同じ | 台帳の行を「Rails リクエスト数 / p50 / p95」の1行にまとめる |
| 値の欠落・空欄・テンプレートにないキー（打ち間違い）がない | `status.sumary` |
| 総合ステータスの色が 🟢 / 🔴、§2 の対応要否が 🟢 / 🟡 / 🔴 で文言と一致、max ルールを満たす | 総合ステータスを 🟡 にする |
| 台帳の「monitor発火」列が件数と継続時間だけ（色なし）で、発火があれば §2 がある | `🔴 critical` / `warning 6回（各10分）` |
| アプリ調査トリガが ON なら §2 がある | |
| `⚠️ 取得不可` に必ず `: <理由>` が続く | `⚠️ 取得不可` だけ |
| monitor を `[名前](…/monitors/ID)（#ID）` の形でだけ参照している | `#297262484` だけ / `mon 297262484` |
| `{{…}}` や「ガイド」が残っていない | |

render が見ないもの（エージェントの判断に残るもの）:

- 出力先 DB に同じウインドウの同名ページが**存在しない**こと（SKILL.md「重複防止」。あれば新規作成せず findings のみ報告）
- 総合ステータスの判定（評価ルールのどの規則に当たるか）と、規則4で 🟢 にした週の理由の1文
- §1 の「monitor 以外で動いた指標」の拾い漏れ（先週比 ±20% 以上・分母と最長継続時間の併記）
- 前週の Decide / Act 候補の反映状況（前週レポートが見つからなければ `previous_actions` を `[]` にする）
- 文章の日本語表現（上の「レポートの日本語表現」）
