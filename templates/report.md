    **この構成の 2 階層**

    - 冒頭の「🔗 調査リンク」= 番号を持たない。読み手がその週の Datadog をすぐ開けるようにタイトル直後に置く。

    - §2 = monitor が発火した週のみ存在する。発火がなければ §2 の見出しごと出力しない。

    **構成の5原則（埋めるときに必ず守る）**

    **A. 一つの数値に一つの住所。** §3.1 の台帳が全指標の唯一の一覧。§1 の表はそこからの抜粋（横断で見るべき指標だけ）、§2 には調査で新たに得た数値（ウインドウ内の p50、遅い SQL の duration 等）だけを書き、再掲しない。

    **B. 発火したものだけ書く。** §2 に節を立てるのは今週 warning / critical が発火した monitor だけ。複数 monitor が同時刻に鳴っていれば同一インシデントとして1節に束ね、1つの原因仮説にまとめる。発火が一つもない週は §2 を出力しない（「該当なし」の見出しすら出さない）。

    **C. 空の枠を作らない。** 該当がない項目は「該当なし」と1行書くか、見出しごと省略する。ヘッダだけの空テーブルは出力しない。

    **D. 読む範囲の目安を示す。** §1 の「総合ステータス」の判定色と一言、および「今週のシグナル変化」で、§2 まで読む必要があるかを判断できるようにする。§1 末尾の「報告の結び」で全体報告の終了を明示し、実際に存在する節だけを案内する。§2 の各節は1行の「シグナル」から始める。

    **E. monitor が鳴っていない異常も拾う経路を残す。** monitor のカバレッジには既知の穴がある（WAF / SES / RDS Reader / `elb_4xx` 等。どれが穴かはプロダクトで違う）。§1「monitor 以外で動いた指標」と §3.1 台帳の「校正メモ」列がその唯一の入口。省略しない。

    **色の決め方**

    判定規則は `references/evaluate.md` が唯一の定義。要点は次のとおり。**色は「読者への要求（対応要否）」専用で、monitor の発火状況には付けない**。発火は件数と継続時間で書く。§1 の判定色は §2 の対応要否のうち**最も重いもの**とする（max ルール。独自判断で緩めない）。判定と発火件数が食い違って見える週は、同じブロック内に理由を1行添える。severity は monitor だけが発行し、レポートでは書き換えない。

### 評価ルール（レポート全体で共通 / 固定文。そのまま出力する）

> 総合ステータスの判定は、下の1〜4を**上から順に適用し、最初に一致したもの**とします。新しい閾値は持ち出しません。材料は monitor の発火とその波及だけです。結果は上の「色の意味」の記号に対応します。
>

1. レポート生成時点で**発火中**の monitor がある → **今週中に人の判断が必要**
2. SLO の**エラーバジェット枯渇・バーンレート** monitor が週中に発火した → 自動復旧でも**今週中に人の判断が必要**
3. 週中に発火して自動復旧した monitor があり、**波及**（SLO / 他レイヤ / 観測されたユーザー影響）が確認できる → **今週中に人の判断が必要**
4. いずれも該当しない → **記録のみ / 対応不要**（**発火があってもここに落ちる**）

規則4で「critical が出ているのに『記録のみ / 対応不要』」となる週は、「総合ステータス」内に判定理由を必ず1文添えます。読み手が矛盾や不当に低い判定と受け取るのを防ぐためです。
